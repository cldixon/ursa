**One real regression: the vertex-table index build (+25%).** A direct A/B confirms it. The released 0.10.0 binary was installed separately for this; the measurement is `--readonly` builds of the same graph, interleaved, three runs each:

| | 0.10.0 | 0.12.0 |
|---|---|---|
| Build time (from the notice) | 6.6 / 6.4 / 6.3 s | 8.0 / 8.1 / 7.9 s |
| User CPU | 31.3–32.1 s | 31.7–31.8 s |
| Peak footprint | 3.79–3.82 GB | 4.10–4.14 GB |

The CPU time is the same, so the extra ~1.6 s is time with fewer cores busy: a new or longer serial phase. The edges-only build (`ge`) did not slow down. With a `.csv.gz` vertex table (track E) the build is now 8.3 s, about the same as Parquet. In 0.10.0 it was 10.3 s against 7.1 s, so #385 helped the CSV path but cost the Parquet path about 1.6 s. Candidate causes, from the changelog:
- the concurrent key interning and renumbering pass (#385);
- counting keys for the uniqueness check (#411);
- the v4 id lookup table (#421).

**The RSS increases are mapped index pages, not more memory.** 0.12.0 memory-maps the stored index (#382), and mapped pages count in RSS once read. By `phys_footprint` (macOS's own accounting, which excludes clean mapped pages), measured on the same database with each version:

| Query | 0.10.0 footprint / RSS | 0.12.0 footprint / RSS |
|---|---|---|
| PageRank | 3.67 / 3.70 GB | **0.88** / 3.63 GB |
| Weak components | 2.25 / 2.27 GB | **0.82** / 2.49 GB |
| Distinct weak components (`check_components_g`) | 5.25 / 4.00 GB | **3.82** / 5.49 GB |
| Distinct strong components (`check_scc_g`) | 5.25 / 5.10 GB | **3.81** / 5.48 GB |

So 0.12.0 uses 27–76% less memory on these steps. **Harness follow-up:** `run.py` records `ru_maxrss`, which now overstates memory for any step that reads the whole index. It should record `phys_footprint` on macOS, and RSS minus file-backed pages on Linux (`VmRSS − RssFile`).

The stored index is 1.5 GiB for `g`, against 1.3 GiB in 0.10.0. That is the v4 id lookup table: 39.65M nodes × 6 B ≈ 0.22 GiB (#421).

**D. `{1,3}` histogram and `ursa.max_paths`: pass, with notes.**
- `hist_1_3` passes in every run, in 0.27–0.33 s (0.10.0: 2.0 s; the full graph errored in round 4). `SHOW ursa.max_paths` gives `10000000`.
- **A low limit doesn't trip `ANY SHORTEST`, by design.** `SET ursa.max_paths = 1000` still returns the histogram, because under `ANY SHORTEST` the limit is "never fewer than one per node of the graph": at least 39.65M here.
- **The error path, on a pattern without a selector:** `MATCH TRAIL (a WHERE a.id = 33127650)-[e]->{1,2}(b)` with `SET ursa.max_paths = 1000` fails with exit 1 and the message `the path search reached 1000 paths, the limit ursa.max_paths sets; give the quantified edge a lower upper bound, keep fewer paths with ANY SHORTEST, or SET ursa.max_paths to a higher limit (0 for none)`. That's a clear error, not a wrong answer. The default 10M limit trips the same way on `TRAIL {1,3}`.

**E. `.csv.gz` vertex table: pass.** 23 / 23 checks. Build 8.3 s against 8.0–9.0 s with Parquet (0.10.0: 10.3 s against 7.1 s).

**F. CSV text with quotes, commas and newlines: pass.**

### Small things noticed (not blocking)

- **A low `ursa.max_paths` is silent when the floor overrides it.** `SET ursa.max_paths = 1000` on an `ANY SHORTEST` query has no effect and says nothing. A one-line notice would help: `ursa.max_paths 1000 is below the node count; ANY SHORTEST uses 39,650,447`.
- **Bad `ursa.max_paths` values give a parser error:** `SET ursa.max_paths = -5` (or `'lots'`) prints `Error parsing '-5' as usize: invalid digit found in string`.
- **A failing query still prints its CSV header to stdout** before the error (`count(*)`, then `Error: …`, exit 1). A script sees a header with no rows.
- **The error for a bare path variable in `COLUMNS` points the wrong way.** `COLUMNS (p AS p)` says `'p' needs its variable, as a.p`, but `p` is the path variable. It should say a path can't be a column, and suggest `path_length(p)` or `vertices(p)`.
