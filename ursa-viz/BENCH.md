# ursa-viz benchmark

A baseline for the graph view: how long until something is drawn, how long
the layout takes, what a frame costs while panning and zooming, what a pick
costs, how much memory it takes and how much it uploads. The numbers below
are from a container with **no GPU**: read the frame times as a check that
the harness works and as a ceiling of software rendering, not as what a
laptop does. The layout and pick times, which run on the CPU, do carry over
(scaled by the CPU).

## How to run it

Build the wasm (see [README](README.md#run-it)), then from `ursa-viz/`:

```sh
bun add --no-save playwright@1.63.0   # once, if Playwright is not installed
bun run bench                         # all of it: about 45 min here, half of it software WebGL2 at 1M edges
bun run bench:report                  # the Markdown tables below, from bench/results.json
```

The bench writes `bench/results.json` (or the path given as its argument).
Environment variables pick a subset:

| variable | default | |
|---|---|---|
| `BACKENDS` | `webgpu,webgl2` | `webgpu` launches Chromium with `--enable-unsafe-webgpu`; `webgl2` with WebGPU disabled, so wgpu falls back to WebGL2 |
| `GRAPHS` | `rmat,grid` | |
| `SIZES` | `1k,10k,100k,1m` | edges, about |
| `MODES` | `multilevel,flat` | |
| `FRAMES` | `120` | frames per pan and per zoom run |
| `FRAME_BUDGET_MS` | `15000` | stop a frame run after this long, past its first 20 frames |
| `PICKS` | `200` | |
| `HEADED` | unset | `1` for a headed window |
| `CHROME` | Playwright's | a Chromium or Chrome binary |
| `NATIVE` | on | `0` skips the native layout timings |

A quick check takes a minute: `SIZES=1k,10k NATIVE=0 bun run bench`.

### On a laptop with a real GPU

Headless Chromium here renders WebGL2 with SwiftShader (on the CPU), and its
WebGPU is a software adapter too. For real frame times, run it headed, on
the laptop's own Chrome, with the machine on power and nothing else busy:

```sh
cargo build -p ursa-viz --features web --target wasm32-unknown-unknown --profile wasm-release
wasm-bindgen --target web --out-dir ursa-viz/pkg $CARGO_TARGET_DIR/wasm32-unknown-unknown/wasm-release/ursa_viz.wasm   # or target/
cd ursa-viz
bun add --no-save playwright@1.63.0
# macOS
HEADED=1 CHROME="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" bun run bench bench/results-laptop.json
# Linux
HEADED=1 CHROME=/usr/bin/google-chrome bun run bench bench/results-laptop.json
bun bench/report.ts bench/results-laptop.json
```

Check the report's backend line says `BrowserWebGpu` for `webgpu` (else
the browser has no WebGPU for this GPU) and that the WebGPU frame sync is
`queue.onSubmittedWorkDone`, not `none`. A headed window paces frames to
the display, so the synced per-frame times have a floor of one refresh
(16.7 ms at 60 Hz); the burst column does not.

## Method

Each case loads `demo/index.html` (the bare view: a generated graph, its
layout in a Web Worker, drawn every animation frame) at 1000 × 700 CSS
pixels, device pixel ratio 1, in a fresh page. The page and the worker each
load the wasm (`wasm-release`).

- **Graphs.** R-MAT (Graph500 parameters, about 8 edges a node: 2^7, 2^11,
  2^14, 2^17 nodes for 1K, 10K, 100K, 1M edges) and a square grid (23², 71²,
  224², 707² nodes), generated by `demo/graphs.js`. Edge counts are the rows
  given to the view; R-MAT's include duplicates and self-loops, and its node
  count includes nodes with no edge.
- **First frame**: from the graph's being ready on the page (wasm loaded,
  graph generated; neither counted) to the end of the first frame drawn with
  positions from the layout. It includes `createView`, starting the worker
  and its loading the wasm (`workerInitMs` in the JSON, 25 to 50 ms), and
  coarse to fine's building the hierarchy, after which every node has a
  position.
- **Layout done**: from the same start to the page's hearing that the
  worker finished: coarse to fine, the end of its schedule; flat, a fixed
  number of iterations (300 at 1K and 10K edges, 30 at 100K, 5 at 1M), so
  for flat the number to read is ms per iteration, measured in the worker.
  Flat needs hundreds of iterations to converge (see the README).
- **Pan and zoom frames**, after the layout is done and with the page's own
  frame loop paused: in each animation frame, `view.pan(±6, ±4)` or
  `view.zoom(1.05 or 1/1.05)` about the centre, `view.render()`, then a sync
  point that waits for the GPU to finish: under WebGL2 a 1-pixel
  `readPixels` on the view's own context, under WebGPU
  `device.queue.onSubmittedWorkDone()` on the canvas's device. The time from
  the call to the sync's return is the frame time: **wall time with a sync
  point**, not GPU timestamps (the view requests no `timestamp-query`
  feature). Median and p95 over up to 120 frames each, after 5 to warm up.
  Also recorded: the CPU time of the calls alone (`cpuMs`), the interval
  between animation frames, and a **burst**: 10 pans and renders in one
  task, one sync, per frame, which is the draw cost without the compositor's
  pacing.
- **Pick**: `view.pick` at 200 pseudo-random pixels (a fixed sequence), with
  the drawing fitted to the view. Pick is a linear scan of the nodes on the
  CPU, so its cost is per node whether it hits or not.
- **Memory**: the page's and the worker's wasm memory (`memory.buffer`), and
  the page's JS heap (`performance.memory.usedJSHeapSize`, with
  `--enable-precise-memory-info`). The server sends COOP/COEP so the page is
  cross-origin isolated, but `performance.measureUserAgentSpecificMemory`
  is not available in headless Chromium; the JSON records the error.
- **Bytes uploaded**: a layout step uploads the positions, 8 bytes a node
  (`x` and `y` as `f32`); the JSON counts the uploads during the layout and
  their bytes. The edges go up once, 8 bytes an edge (`edgeIndexBytes`).
- **Native**: `ursa-core`'s `fa2_multilevel` example in `bench` mode, on the
  same graphs: the hierarchy, coarse to fine in one call
  (`layout_fa2_multilevel`) and flat ForceAtlas2 per iteration (up to 100
  iterations or about 2 s), built with `--no-default-features` (one thread,
  as the browser runs it) and with rayon (all cores):

  ```sh
  cargo run -p ursa-core --release --example fa2_multilevel -- bench 1k,10k,100k,1m rmat,grid
  cargo run -p ursa-core --release --no-default-features --example fa2_multilevel -- bench
  ```

What stands out, for setting targets:

- **The first frame is quick; the layout is the wait.** Coarse to fine has a
  position for every node once the hierarchy is built, so under WebGPU the
  first frame comes in 74 to 160 ms up to 100K edges and 1.1 s at 1M (0.7 s
  of it building the hierarchy, 0.3 s `createView`). Layout done is 0.1 to
  1.6 s at 10K edges, 5.3 s (R-MAT) and 16 s (grid) at 100K, and 8.2 s and
  32 s at 1M.
- **Grids cost far more than R-MAT at the same edge count**: 9.4 s against
  3.5 s natively at 100K edges, 21 s against 5.3 s at 1M. A grid has 3 to
  4 times the nodes per edge, coarsens into more levels (15 against 11 at
  1M), and every level gets the schedule's iterations. A structured graph is
  the case to target, not R-MAT.
- **wasm is about 1.4 times slower than native on one thread** (flat at 1M
  R-MAT edges: 529 ms against 378 ms an iteration; coarse to fine 7.8 s in
  the worker against 5.3 s), and native on 4 threads is 2.9 times faster
  again (1.85 s). A threaded wasm build (SharedArrayBuffer, COOP/COEP)
  would be worth up to that.
- **The view's own cost per frame is small**: pan or zoom plus render is 0.2
  to 0.35 ms of CPU up to 1M R-MAT edges, 1.1 ms at the 500K-node grid. Drawing is the GPU's, and here it is
  SwiftShader's: 4.4 s a frame at 1M edges, 0.5 s at 100K.
- **Software WebGL2 starves the layout of positions.** A frame that takes
  seconds holds the page's thread, so at 1M edges the page took the
  worker's positions 2 or 3 times in the whole layout (WebGPU, ~50), and the
  first frame came after 31 s. The worker kept its pace (9.9 s against
  7.8 s, sharing the CPU); the page just never showed it.
- **Pick is a linear scan**: 0.55 ms at 131K nodes, 1.8 to 2.2 ms at 500K.
  Fine for a click; too slow for hover at a few million nodes.
- **Memory is the worker's**: at 1M edges the worker's wasm memory is 107
  to 116 MiB (the hierarchy, every level's adjacency) and the page's 54 to
  82 MiB (the view's copy of the graph and positions). wasm
  memory never shrinks, so a second graph in one page starts from there.
- **Uploads are positions only**, 8 bytes a node a time: 1 MiB a post at 1M
  R-MAT edges, 4 MiB at the 1M-edge grid, about 10 posts a second. The
  100K-edge grid made 190 posts over its 16 s layout, 76 MB in all.

## Growing a layout

A warm start (`fa2_grow`, #442), natively, by `fa2_multilevel`'s `grow` mode:
each R-MAT graph is laid out coarse to fine, then one node of degree 8 to 32
gains 16 or 100 new neighbours, a third of them also tied to another node
drawn. Not part of `bun run bench`; to rerun it:

```sh
cargo run -p ursa-core --release --example fa2_multilevel -- grow 1k,10k,100k,1m 16,100
cargo run -p ursa-core --release --no-default-features --example fa2_multilevel -- grow
```

Run 2026-11-21 on the same machine (4 cores), best of five. *build* is
`Topology::build` and its undirected view for the grown graph, *place* is
`fa2_grow` (the spiral, the masses, the masks), *run* is the whole warm
schedule, 60 iterations. *held* is how the old nodes are held: `x10` is ten
times the inertia within two hops of a new node and fixed beyond, `fixed` is
all of them (more than 5,000 nodes). Moves are of the old nodes, in % of the
width of the drawing's connected part; *nearest* is the least distance from
a new node to any other, in the same unit.

One thread, as the browser runs it:

The moves are the same on both, to the bit.

- **Adding 100 neighbours to a laid-out 1M-edge graph costs 64 ms on one
  thread, 40 ms on four**, of which 52 and 25 ms rebuild the adjacency. That
  is under the design's 100 ms from click to frame, natively; the engine's
  `hop` and `induced_edges` (about 10 ms each), the delta and the frame are
  on top, and wasm is about 1.4 times slower than native on one thread. The
  first frame needs only *build* and *place*: the schedule can run over the
  frames after it.
- **Holding the drawing whole is what makes that so.** With every old node
  free at ten times the inertia (`GROW_FREEZE=10000000 GROW_REACH=4000000000`),
  the same 60 iterations take 1.7 s at 1M edges and 170 ms at 100K on four
  threads, and move the old nodes 0.4% and 0.1% of the width on average.
- **A finished layout is not at rest.** ForceAtlas2 keeps carrying leaves
  outwards long after the shape has settled, so 60 more iterations move
  nodes that have nothing to do with what was added: with one node added and
  every old node free at ten times the inertia, 2.1% of the width on average
  and 11.5% at most in the 128-node graph (0.12% and 1.6% in the 2,048-node
  one). Freeing only the nodes within two hops brings that to 1.0% and 0.03%.
  R-MAT's 128-node graph is the hard case: two hops from a hub is most of
  it, and 16 new neighbours are an eighth of the graph. The largest moves
  left are of old nodes that gained an edge to a new node across the drawing.
- **The expanded node is held.** Free, a node of degree 30 that gains 16
  neighbours moves 18% of the width in the 128-node graph: its ForceAtlas2
  mass is `deg + 1`, so everything repels it harder than a moment before
  (`GROW_FREE_PARENT=1 GROW_REACH=4000000000`).

## The highlight layer

What a highlight costs a frame, and what setting one costs (#435). After the
pan and zoom runs, `bun run bench` repeats the burst (ten frames in one
task, each a pan and a render, one sync at the end) with a path of 100
nodes highlighted (99 wide edges, 100 nodes in front with halos, everything
else dimmed), then with one node hidden as well (the edges' shader reads
the flags). It also times `setHighlights` for that path (20 times, cleared
in between) and `setSelection` of one node (50 times), and counts the bytes
each uploads. R-MAT, coarse to fine, the same container with no GPU, and
busier than when the tables above were measured (its plain burst at 1M
edges is 6.1 s here, 4.4 s there): compare along a row, not with them.

| backend | nodes | edges | burst, ms/frame | with the path highlighted | and a node hidden | `setHighlights`, ms (median) | `setSelection`, ms (median) |
|---|---|---|---|---|---|---|---|
| webgl2 | 2,048 | 10,000 | 81.2 | 84.0 | 84.8 | 0.16 | 0.03 |
| webgl2 | 16,384 | 100,000 | 550.8 | 561.5 | 608.1 | 0.33 | 0.07 |
| webgl2 | 131,072 | 1,000,000 | 6,150 | 6,335 | 6,392 | 0.44 | 0.46 |
| webgpu | 131,072 | 1,000,000 | 0.14 | 0.16 | 0.13 | 0.37 | 0.42 |

- **A frame with a highlight costs what a frame costs**, within the noise
  of this machine: 3% more at 1M edges on software WebGL2 (one burst each
  at that size, at six seconds a frame), where every one of the million
  lines is rasterised on the CPU either way. The layer adds 99 quads, 100
  discs and one uniform. The WebGPU row is the submit's CPU cost alone (see
  the caveats): it says the wasm side adds nothing measurable.
- **A hidden node** switches the edges to the pipeline that reads the flags:
  4% at 1M edges here, 10% at 100K, which is also within the run-to-run
  spread. A real GPU will say whether a per-vertex flag and a discard cost
  anything; the view only pays it while a node is hidden.
- **Setting a highlight uploads no edges.** A path of 100 nodes writes 400
  bytes of flags (100 runs of one node, four bytes each; 780 a set here,
  counting the clear before it) and 3,584 bytes of instances (99 edges of 16
  bytes, 100 nodes in front of 20), in 0.4 ms at 131K nodes. The graph's
  million edges (8 MB of indexes) are not written.
- **A selection of one node** writes 8 bytes of flags (the node deselected
  and the node selected) and 20 for the node drawn in front. Its 0.4 ms at
  131K nodes is the CPU's: the view copies and compares the flags, a byte a
  node, to find what changed.
- An earlier draft drew the nodes in front by running the node pipeline a
  second time over every node, leaving the others out in the shader. On
  software WebGL2 that cost 26 ms a frame at 2,048 nodes (a third of the
  frame), which is why they have a buffer of their own.

## Rings and layers

The fixed layouts (`layout_rings`, `layout_layers`, #436), natively, by
`ursa-core`'s `layout_levels` example: each R-MAT graph whole, every node
levelled by its distance from node 0 and the unreached nodes left without a
level. That is the largest neighbourhood each graph has; a `hop` result is
usually far smaller. Not part of `bun run bench`; to rerun it:

```sh
cargo run -p ursa-core --release --no-default-features --example layout_levels
```

Run 2026-11-21 on the same machine, one thread (both layouts are serial, so
rayon changes nothing), the median of five, the adjacency already built.
*mean edge* is the mean edge length before and after the four barycentre
sweeps, in ring or layer spacings.

| graph | nodes | edges | nodes per level | rings ms | rings mean edge | layers ms | layers mean edge |
|---|--:|--:|---|--:|--:|--:|--:|
| 1k | 256 | 751 | 1, 79, 99, 6 (71 without) | 0.22 | 4.40 → 3.46 | 0.10 | 14.6 → 10.3 |
| 10k | 2,048 | 8,334 | 1, 433, 876, 78 (660 without) | 2.1 | 29.5 → 25.2 | 1.2 | 103 → 77 |
| 100k | 16,384 | 88,822 | 1, 2,082, 7,461, 708, 12 (6,120 without) | 21 | 214 → 191 | 12 | 752 → 550 |
| 1m | 131,072 | 928,785 | 1, 9,706, 60,268, 6,390, 60 (54,647 without) | 305 | 1,667 → 1,481 | 166 | 5,872 → 4,394 |

- **A neighbourhood of a few thousand nodes is laid out within a frame**
  (2 ms at 2,048 nodes), and one of 16,384 nodes in about one and a half
  (21 ms). Both grow with the adjacency: about 40 ns an adjacency entry a
  sweep for rings.
- **At 1M edges rings take 0.3 s**, where coarse to fine takes 7.5 s. In the
  browser (`tests/browser/view.ts`, the neighbourhood of node 0 within three
  hops: 76,365 nodes, 999,881 edges) the worker took 0.99 s for rings and
  0.47 s for layers, building the adjacency included, and posted one
  message.
- **The sweeps shorten edges by 11 to 27%** on these graphs. R-MAT is the
  hard case: a level's nodes share most of their neighbours, so no order is
  much better than another. On karate's shortest paths the order leaves no
  crossing.
- **On karate** the worker took about 2 ms for either layout
  (`view.ts`): two hops from node 0 are 26 nodes on two rings, the nearest
  two 84 px apart on a 1000 by 700 canvas.

## Deltas

What a scene that changes in place costs (#441): a view made from a result
(`createViewFromResult`) takes a delta of 100 new nodes and 300 new edges
(an expansion: each new node joined to one hub and to two random nodes),
then its inverse, 30 times. `ONLY="delta rmat" bun tests/browser/view.ts`
measures it in Chromium on R-MAT with 131,072 nodes and 1,000,000 edges,
software WebGL2, the same container with no GPU;
`cargo test -p ursa-viz --no-default-features --release --test delta_scale -- --nocapture`
measures everything but the GPU writes natively, on a uniform random graph
of the same size.

| | bytes uploaded | `applyDelta`, median | its inverse | the first, cold |
|---|---|---|---|---|
| Chromium, wasm, WebGL2 | 5,172 | 0.5 ms | 0.3 ms | 2.0 ms |
| native, no GPU writes | 5,252 | 0.13 ms | 0.02 ms | 0.31 ms |

The issue's budget is 64 KB and 2 ms outside the frame.

- **The bytes are the delta's**: 100 nodes of 16 bytes (position, radius,
  colour) and 4 of flags, 300 edges of 8, and the radii of the older nodes
  that gained a neighbour (nodes are sized by degree), 4 bytes a node in
  runs: 5 KB, against the 8 MB of edge indexes and 2.6 MB of node data the
  view holds. The delta itself is 3,880 bytes of UGR.
- **The time is the delta's too**: nothing in `applyDelta` reads every
  node or edge. One build back, a delta and its inverse together took
  0.95 ms on R-MAT with 100,000 edges and 0.90 ms with 1,000,000 (200
  pairs each). More than half of that was the writes of the older nodes'
  radii, some 200 scattered nodes each way: the same expansion with every
  edge to the one hub took 0.43 and 0.24 ms. (Those radii were then written
  with their colours, two writes a run; now alone, which is the 0.8 ms of
  the table's pair.)
- **The largest of the 30 was 4.9 ms**, once: a pause of the page's, not of
  the delta's (the next was back at the median).
- **The first delta** pays for the wasm's first run of this code, and no
  more than that: a view made from a result has room for a sixty-fourth
  more nodes and edges than it starts with (rounded up to a power of two:
  1,048,576 edges here), on the GPU and in the result's arrays. Before it
  had, the first delta took 11 to 13 ms, most of it moving the result's
  arrays, native or wasm.
- **The delta that outgrows the buffers** doubles them: the GPU copies what
  they held (`copyBufferSubData` on WebGL2, an index buffer included) and
  nothing is uploaded again. `tests/browser/view.ts` checks on the karate
  club that the pixels away from the additions are untouched by it.
- **Undo** is the inverse delta: 0.3 ms, and 4 bytes for each older node
  whose radius goes back. With the positions saved before the step (an
  undo after the layout has moved), it also uploads 8 bytes a node, as one
  layout step does.
- **Read back:** after the 31 deltas and their inverses, the frame is the
  first frame, byte for byte; and on the karate club after each of a
  growth, a growth past the buffers, a removed node, removed edges and a
  refused delta.
- **`info()`** after a delta: 0.5 ms here (its first call) with nothing
  hidden and no colour column, where it reads no node or edge. With a node hidden it counts the
  shown edges (every edge is read), and with a colour column the nodes of
  each category, once after each delta.
- **What it took.** Three things read the whole graph in the first draft,
  and together cost 2.2 ms a delta in Chromium: fitting the camera (the
  bounds of every position, 1.4 ms at 131K nodes), comparing every node's
  flags to find the changed ones, and, for an undo, the model reading every
  edge to see that none still named the nodes taken off (0.75 ms native).
  Now the camera's bounds are widened by the new nodes', the new nodes'
  flags are written without reading the others, and the model keeps the
  greatest node index its edges name, as it rises along them.

## Caveats

- **No GPU.** WebGL2 runs on SwiftShader, on the same 4 cores as the layout
  worker and the page, so at 100K edges and up the frame times are the
  CPU rasterising lines, and they slow the layout too (compare the WebGPU
  run's layout times). Headless WebGPU here is a software adapter whose
  `onSubmittedWorkDone` (like the view's snapshot) rejects with "A valid
  external Instance reference no longer exists", so its frame times are the
  submit's CPU cost alone, not the GPU's work: they say what the wasm side
  costs, about 0.2 to 0.3 ms a frame at any size. Neither is a laptop's GPU.
- **The synced frame time includes pacing.** Under WebGL2, `readPixels`
  waits for the frame before it, which the compositor paces at 60 Hz, so
  small graphs read 16.7 ms whatever they cost; the burst column does not.
- **Shared machine.** The container's cores are shared with other work;
  runs vary by 10 to 20 %.
- **A busy page lingers.** The first case after software WebGL2's 1M-edge
  R-MAT read 5.8 s to its first frame, the previous page's work still
  draining; it is rerun alone in `results.json` (marked `rerun`).
- **A shared `CARGO_TARGET_DIR`.** Worktrees that share a target directory
  can leave cargo running another worktree's build of the example (it then
  panics with `unknown graph bench`); `touch ursa-core/examples/fa2_multilevel.rs`
  and rerun.
- **One run each.** The medians are over frames, not over runs; the first
  frame and layout times are single measurements.
